# Employee access: staged rollout contract

Status: **future employee assigned-work access is NOT implemented or enabled**.
The first phone acceptance test belongs to Wes, keeping his existing full
management access and all screens. Mobile layout changes do not imply a role
change. No employee account, invitation, mapping, or live permission change is
part of this source work.

## Phase 1: existing-role safety, independently reviewable

The companion mobile UI must follow current backend capabilities:

- Production setup / pour / strip / issue controls use the existing granular
  production permissions.
- Installation Start / Complete / Hold / Resume call
  `save_walls_installation_activity`, which currently requires management.
  Do not show those actions for `field_progress` alone and do not grant management
  merely to make them work.
- `field_progress` currently permits reporting an installation issue; preserve
  that useful action without granting schedule editing or issue resolution.
- Readiness, closeout, crew/resource editing, QC release and plan changes remain
  separately controlled. There are no new employee grants.

### Internal conflict-rebuild migration

`20261023150216_planner_conflict_rebuild_internal_only.sql` has one effective
statement: revoke direct EXECUTE on
`public.rebuild_weekly_planner_conflicts(date)` from PUBLIC, anon and authenticated.

This helper deletes/rebuilds derived conflict rows. Calling it is a write, even
though its existing function body checks planner view. It is not called directly
by the frontend or Edge Functions. Its four current callers are:

1. `generate_weekly_planner` — edit gate.
2. `save_weekly_planner_inputs` — edit gate.
3. `save_weekly_planner_section` — section-specific edit gate.
4. `approve_weekly_planner_section` — section-specific approve gate.

All four are SECURITY DEFINER. Read-only inspection of the hosted catalog on
23 October 2026 found all four and the helper owned by postgres. Owner execution
continues after the client grant is removed. Approval-only users are why this
fix does **not** replace the helper's old view predicate with an edit predicate.

Effects:
- No authenticated client, including an admin JWT, can call this internal helper
  directly. Admins keep all current screen-level management workflows through the
  guarded public APIs.
- Viewer, unassigned and disabled users cannot directly cause recomputation.
- Existing editor, scoped approver and publisher behavior is preserved.
- The helper body, signatures, owners, all other function/table ACLs, role/access
  rows and operational data are unchanged. Existing service-role ACLs are not
  altered.
- This does not add assigned-only reads, change `allowed_sections` read semantics,
  or certify every API as read-only.

### Validation and deployment boundary

The migration is generated by pinned Supabase CLI 2.122.0 and committed as source.
Local static validation verifies exactly one ACL reduction, checks all current
caller definitions, and rejects any direct client/Edge call.

The disposable PostgreSQL17 CI test uses synthetic users and a rollback
transaction. It checks anonymous/authenticated ACLs, owner execution, actual
viewer rejection with unchanged state, admin generation/inputs/saves/approvals,
section-limited editor save, approve-only success, out-of-section rejection,
publisher success, and disabled/unassigned denial. Existing full workflow CI
also applies this migration before exercising its admin workflows.

Before an authorized production rollout:
1. Recheck exact deployed definitions and all call sites for drift. Confirm all
   callers remain SECURITY DEFINER and their owners retain helper EXECUTE.
2. Require the exact candidate's CI to pass and inspect the synthetic permission
   test log, not only a green static check.
3. Obtain explicit approval for production migration application. Merging this
   source PR is not evidence of application and does not authorize a live SQL run.
4. Apply only the reviewed migration through the approved deployment path.
   Mobile frontend can ship independently; no frontend direct helper call exists.
5. Verify catalog ACLs and normal manager workflows using authorized test methods.
   Do not invoke the business helper or create employee accounts merely to verify
   a grant change.

Reversal, only with explicit production authorization, is
`GRANT EXECUTE ON FUNCTION public.rebuild_weekly_planner_conflicts(date) TO authenticated;`
because that restores the prior authenticated API grant. **It reopens the
viewer-triggered mutation**, so prefer fixing a discovered internal caller instead
of rolling back broadly. Do not regrant PUBLIC or anon. No automatic rollback or
deployment is included.

## Phase 2: explicit employee identity and assigned-work access

Do not infer account identity from the roster's display name. Current roster and
crew names are human-readable scheduling strings; they are not an authorization
mapping. Do not call a view “My assignments” while returning the whole company
board, and never grant `app_user_roles.can_write=true` as an employee shortcut:
that flag is a broad Operations admin override regardless of its role label.

The future design needs user-approved answers before code or provisioning:

- Which employee is the pilot? Who owns and can recover the individual work
  mailbox? Is the phone personal or shared?
- Which stable employee identifier is authoritative? Who verifies its mapping to
  the Supabase Auth UID and handles termination/reassignment?
- Is plant-wide Walls visibility acceptable, or only assigned table/run/job/crew?
- Which exact duty may the employee update: setup, poured quantity, stripped,
  count, report problem, field status? Who may correct mistakes?
- Who grants/revokes assignments and for what effective date range?
- Does anyone need both plant and field access? What is the intended union?

### Proposed data contract (design only; no schema migration)

Use explicit administrator-maintained relations, never a user-editable JWT claim
or display-name match:

- Employee identity: stable employee ID, unique Auth UID, active status,
  verified-by/verified-at and auditable change history.
- Work assignment: employee/crew ID, exact wall job and optionally production run
  or field activity ID, date/time validity, allowed capabilities and enabled flag.
- Crew membership: stable IDs and effective dates; only needed if team-level scope
  is chosen. Do not copy current free-text names into authority automatically.
- Capability grants: defaults false; no master-schedule, financial, admin,
  engineering, QC-release, approval or publication capabilities by implication.
  Inventory count scope is separate from ordering, receiving and configuration.

A missing, disabled, expired or ambiguous identity/assignment must deny access.
Revocation must remove effective authorization across independent grant paths,
not merely hide navigation or disable one employee-access row.

### Read contract

A server-owned employee projection should allowlist fields such as job number,
assigned date/task/table/run, address if needed, operational status, safety/hold
information, and released document links. Filter by verified assignment and duty
before returning JSON. Do not reuse the broad master snapshot minus one private
field.

Test direct REST tables, every snapshot/RPC, planner packets/source snapshots,
history, and assistant context as alternate read paths. If direct tables contain
unneeded private fields, revoke client reads or expose a safe projection rather
than relying only on row filtering. All SECURITY DEFINER functions must enforce
the same assignment rules themselves.

### Write contract

Prefer narrow command APIs rather than exposing full management save functions:

- A field-status command takes activity ID, requested transition, expected
  version and optional work note; it must not accept job, crew, date, scope,
  readiness, closeout or identity replacement.
- Setup/pour/strip commands check the caller's exact assigned duty and existing
  production gates. Strip is never QC release or shipment authorization.
- Count entry checks assigned inventory scope, explicit nonblank integer input,
  optimistic version, and bounded/repeated-tap behavior.
- Problem reporting can create an audited concern/hold according to the approved
  process; resolution authority is separate.
- Attribute records to the verified Auth identity on the server, not a submitted
  “employee name.” Include reliable saved/failed/unknown-outcome UX.

### Required tests and release gate

Test every narrow role's allow/deny matrix directly against the backend, with
synthetic wrong-user, wrong-job, wrong-crew, wrong-division, expired/disabled,
tampered-ID, stale/null-version and duplicate-operation cases. Assert both
returned data and unchanged denied-operation records/audit. Preserve management
regressions. Verify no role name unexpectedly enables admin.

After Wes accepts the phone UI, obtain a separate employee-pilot decision and
identity/scope confirmation. Start read-only. Enable a small write capability
only after the required backend, phone, retry and account-handoff tests pass.
Keep this employee phase open; it is not completed by a mobile stylesheet or the
internal-helper ACL migration.

## Frontend completion boundary (2026-10-25)

Restricted Overview and Today use the same capability-aware launcher. Neither
claims that company data is personally assigned. Production and Field Work stay
inside their own module tabs; Inventory shows only the granted scope/actions.
Employee Today omits the Report a Walls issue shortcut for the first rollout.
Management's existing screens and authority remain intact.

An explicitly permitted employee Crew schedules route uses only the dedicated
`get_employee_approved_crew_packs` endpoint, active approved packets, and a
field-allowlisted read-only client cache. It does not widen the management planner
loader or grant the `weekly-planner` view. Source must ship together with the
separately reviewed backend contract before that employee feature is usable.

These are presentation/client-read changes, not backend isolation. No personal
identity/assignment mapping, account grant, production write capability, inventory
scope or live operational record changes are included. The separate backend
projection/policy candidate and Phase 2 authorization requirements remain gates.
Manual Refresh is visible because restricted raw realtime payloads are not part
of the safe employee read contract; confirmed writes still refresh via the
approved loader rather than polling.
